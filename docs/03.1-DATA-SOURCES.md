### Effect-Implementation Index and Curated Coverage Overlays

| Property | Value |
|---|---|
| **Source ID** | `effect-implementation-index` |
| **Local repo path** | `data/metadata/effect-implementation-index.json` (generated; never hand-edited) |
| **Generator** | `scripts/build-effect-implementation-index.mjs` (`pnpm effect-index`); validates its output against `EffectImplementationIndexSchema` from the registry `dist`, so build the registry first |
| **Gate** | `pnpm effect-index:check` regenerates in memory and fails on any drift from the committed file (CI `ci.yml`). Editing an overlay without regenerating fails it |
| **Consumers** | `/debug/effects` viewer (WP-484 / D-24289); `/coverage` counts every card type from it (WP-880 / D-24829) |
| **Row shape** | One row per card x mechanic: `extId`, `name`, `set`, `scope` (`hero` / `villain` / `mastermind` / `scheme`), `mechanic`, `status`, `handler`, `wp`, `decision` |

Hero and villain rows come from the two committed mechanic ledgers
(`docs/ai/coverage/hero-mechanic-ledger.json`, `villain-mechanic-ledger.json`)
joined verbatim. The mastermind-tactic, Master Strike, and Scheme rows are
read from `data/cards/*.json` plus the three curated overlays below, so
**identity always comes from the card data** and an overlay curates only
`status`, `handler`, `wp`, and `decision` (the WP-493 generated-identity /
curated-provenance split). Every tactic, Mastermind, and Scheme line
therefore appears in the index with no overlay entry.

**Curated overlays** (all under `scripts/coverage/`; each file's `_comment`
is the field-level contract):

| Overlay | Feeds | Introduced | Keyed by | Orphan keys |
|---|---|---|---|---|
| `tactic-provenance.json` (`tactics`) | One mastermind-scoped row per Mastermind tactic card; mechanic = the tactic slug | WP-507 / D-24313 | `${setAbbr}-mastermind-${mastermindSlug}-${tacticSlug}` | **Silently ignored** (the generator iterates the card data, not the overlay; a stale key just never matches) |
| `strike-provenance.json` (`strikes`) | One mastermind-scoped row per Mastermind; mechanic `master-strike` | WP-867 / D-24810 | `${setAbbr}-mastermind-${mastermindSlug}-master-strike` | Fail the build |
| `scheme-provenance.json` (`schemes`) | One scheme-scoped row per Scheme per printed line kind (`setup`, `special-rules`, `twist`, `evil-wins`, `good-wins`) | WP-879 / D-24828 | `schemes[${setAbbr}-scheme-${schemeSlug}][mechanic]`, so status is per line, never per Scheme | Fail the build: a key matching no Scheme, or a mechanic the Scheme does not print |

Rules common to all three:

- **Absent row = `unmarked`** with blank `handler` / `wp` / `decision`: "no
  curated evidence", never a fabricated attribution and never "broken".
- Add one row when a resolver ships; no generator change is needed.
- The Scheme overlay additionally fails the build on an `executable` row with
  a blank `handler` (the evidence rule, enforced rather than only listed). It
  is seeded only for Schemes with live-verify evidence (the 8 Core and 4
  Captain America 75th Schemes).
- The strike overlay is backed by an engine test
  (`mastermindStrike.unresolved.test.ts`) that fails if an `executable` or
  `deferred` strike row records a hollow effect at runtime.

**Related overlay: `subsystem-coverage.json`.** Not read by the index
generator directly. The two ledger generators (`scripts/villain-mechanic-ledger.mjs`,
`scripts/hero-mechanic-ledger.mjs`) read it and emit status `subsystem`
(implemented by a non-`[effect:X]` subsystem, e.g. `setup:require-to-defeat`
or `scoring:dynamic-vp`) instead of `unmarked`; the status then reaches the
index through the ledgers. Villain entries are keyed by card ext_id (`cards`);
hero entries are keyed card -> mechanic (`heroes`), because one hero card can
mix implemented and unimplemented mechanics. A card joins only once its
subsystem implementation is merged (WP-548 / D-24357, WP-559 / D-24368).
Gated by `pnpm ledger:villains:check` and `pnpm ledger:heroes:check`.

**Related overlay: `mechanic-provenance.json`.** Mechanic -> `{ wp, decision }`
attribution consumed by the mechanic ledgers; a missing key reads blank.

### Setup-Time Derived Data (In-Memory)

These fields are built at `Game.setup()` from registry + config inputs.
They live in `G` and are immutable during gameplay. Moves never query
the registry — they use these pre-resolved fields.

| G field | Built from | WP | Purpose |
|---|---|---|---|
| `G.villainDeckCardTypes` | Registry card type classification | WP-014B | O(1) card type lookup during reveal |
| `G.cardStats` | Registry hero/villain stat values | WP-018 | Economy: attack, recruit, cost, fightCost |
| `G.heroAbilityHooks` | Registry hero card text parsing | WP-021 | Hero ability effect execution |
| `G.mastermind` | Registry mastermind + tactics data | WP-019 | Boss fight resolution |
| `G.matchConfiguration` | `MatchSetupConfig` (9 locked fields) | WP-005A | Match identity and composition |
| `G.hookRegistry` | Rule definitions (data-only) | WP-009A | Rule trigger/effect pipeline |
| `G.cardKeywords` | Registry villain/henchman ability text | WP-025 | Board keywords (Patrol/Ambush/Guard) per card |
| `G.cardDisplayData` | Registry card display fields (`name`, `imageUrl`, `cost`) | WP-111 | UIState card-display projection; surfaced via `UICityCard.display` / `UIHQState.slotDisplay?` / `UIPlayerState.handDisplay?` / `UIMastermindState.display` |
| `G.schemeSetupInstructions` | Registry scheme data (MVP: `[]`) | WP-026 | Scheme board config; replay observability |
| `G.activeScoringConfig` | `ScenarioScoringConfig` via optional 4th parameter to `buildInitialGameState` (D-6703) | WP-067 | Marks the match as PAR-scored; read by future `buildUIState` PAR gate (payload deferred per D-6701) |

**Persistence note:** These fields are runtime-only. `G` is never
persisted to a database. Snapshots store zone counts only, never full
card arrays or derived fields. See ARCHITECTURE.md Section 3.

### Match Setup Configuration

| Property | Value |
|---|---|
| **Source ID** | `match-setup-config` |
| **TypeScript contract** | `MatchSetupConfig` in `packages/game-engine/src/matchSetup.types.ts` |
| **Fields** | 9 locked fields (D-1244): `schemeId`, `mastermindId`, `villainGroupIds`, `henchmanGroupIds`, `heroDeckIds`, `bystandersCount`, `woundsCount`, `officersCount`, `sidekicksCount` |
| **Format conventions** | The five entity-ID fields (`schemeId`, `mastermindId`, `villainGroupIds`, `henchmanGroupIds`, `heroDeckIds`) use the locked set-qualified form `<setAbbr>/<slug>` (e.g., `"core/legacy-virus"`, `"core/black-widow"`) per D-10014. Bare slugs, display names, and flat-card keys are rejected by `validateMatchSetup`. The `<setAbbr>/` prefix disambiguates collisions across loaded sets — slugs collide for 51/307 hero instances, 6/106 mastermind instances, 4/126 villain group instances, and 4/191 scheme instances per the WP-113 PS-8 probe. The four count fields are non-negative integers. |
| **Schema alignment** | JSON schema must match TypeScript contract exactly; `additionalProperties: false` enforced (D-1244 through D-1248) |
| **Mutability** | Immutable after match creation |
| **Lifecycle** | Client submits -> server validates -> passed to `Game.setup()` |
| **Trust model** | Validated by Zod at server boundary; `validateMatchSetup` runs inside `Game.setup()` on every match-create — wired by `apps/server/src/server.mjs` calling `setRegistryForSetup(registry)` at startup, before `Server({ games, origins })` is constructed (D-10014). Engine throws in `Game.setup()` on invalid config; the lobby's `validateSetupData` returns the throw message as a 400 response. |
