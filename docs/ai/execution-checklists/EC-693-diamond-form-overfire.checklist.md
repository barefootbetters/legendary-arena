## Locked Values (do not re-derive)
- Grant: **+3 Recruit** to the playing player's turn economy, **per qualifying defeat that turn** (model per D-24467).
- Trigger: a defeat of a City Villain (`fightVillain` success, incl. Skrull) OR the Mastermind (`fightMastermind`, RS-1 semantics), during the turn Diamond Form is in play; reset at the turn boundary. Resolution rides the existing `onMove` — **no new resolve call**.
- The new wait-and-see condition slug is added to BOTH `WAIT_AND_SEE_CONDITION_TYPES` AND an `evaluateCondition` case (+ `describeFailedCondition`) — never one without the other (exact literal chosen at execution, recorded in D-24467).
- **Edge-triggered:** exactly one +3 per qualifying defeat EVENT (consumed/counted), never a sticky boolean the `onMove` resolver re-reads; `defeat → recruit → defeat → play` = **+6, not +9**, per D-24467.

## Guardrails
- Reuse the wait-and-see mechanism; add ONLY a condition + a defeat signal. Do NOT add a resolve call, and do NOT invent a parallel trigger — `onMove` already re-checks post-fight.
- **The defeat signal must be oracle-safe:** write it only while **any** deferred grant is pending (`G.deferredConditionalGrants` non-empty) so it never enters `G` for a game with no pending grant — OR plan a recorded, explained re-pin via `record-game-fixture.mjs` (never hand-edited). An unconditional flag (the `hasActedThisTurn` pattern) WILL move both oracles; do not ship that silently. Confirm oracle byte-stability against a fixture carrying an UNRELATED deferred grant (e.g. `recruitMadeThisTurnAtLeast`) + a defeat, not just a no-deferred-grant game.
- Moves never throw; the condition handler safe-skips malformed/absent state (it falls through `default → false`).
- The `diamond-form` encoding is **regenerated by the pipeline, never hand-edited** (WP-633): a clean regen reproduces the committed `data/cards/*.json` byte-for-byte.
- Drift lockstep (`WAIT_AND_SEE_CONDITION_TYPES` ↔ evaluator cases) is a **runtime** assertion (engine tests are not typechecked — D-24372), with a NEGATIVE assertion that fails for a synthetic listed-but-unhandled type.
- Diamond Form is a **HERO** card — regenerate the HERO feeds, not the villain ones: `pnpm -r build && pnpm ledger:heroes && pnpm effect-index && pnpm mechanics:metadata`, then `ledger:heroes:check` + `effect-index:check` + `mechanics:metadata:check` + `cards:check` (WP-633) all exit 0. Run EVERY `:check` even where a feed shows no diff (`core/emma-frost` indexes `mechanics:["draw"]` only today, so the ripple is unknown until each runs). Do NOT run `ledger:villains` (a hero card yields no diff → masks a miss). Confirm each diff is real (not LF/CRLF churn) before committing.
- If the repeatable model requires changing the numeric-threshold doctrine, UPDATE the `deferredConditionalGrants.ts:1-32` doctrine comment (and the D-24377 rationale) to match — do not leave the comment contradicting the code.

## Common Failure Smells
- Diamond Form still grants +3 on play → the flat `onPlay recruit:3` marker was not replaced, or the card-data regen was skipped.
- A second resolve call was added at the fight sites → double-fire vs `onMove`; the grant applies twice per defeat.
- The grant fires once but not twice in a two-defeat turn → the one-shot path was reused without the D-24467 repeatable model (the scaffold should have caught this).
- A hash oracle moved unexpectedly → the defeat signal was written UNCONDITIONALLY (entered `G` for a non-Diamond-Form game) instead of gated; investigate before re-pinning.
- A `:check` gate green locally but CI red → a second-order derived artifact (effect-index off the ledger) was not regenerated.
