## Goal

Mastermind **tactic** cards appear **nowhere** in the effect-implementation
index (`data/metadata/effect-implementation-index.json`), so `/debug/effects`
cannot show whether a tactic's printed **Fight:** ability is implemented. The
index is a verbatim join of the **hero + villain** mechanic ledgers only, and
tactics live in neither. This WP adds a **third, `mastermind`-scoped feed** so
every mastermind tactic shows up as a `card × mechanic` row with an honest
`status` (executable when a `tacticHandlers.ts` resolver exists, unmarked
otherwise). It makes the WP-497 arc's coverage visible: today a defeated-but-
inert tactic is invisible until someone plays it (as reported 2026-08-06 for
core Magneto — `/debug/effects` shows only the hero `dodge` row and the
mastermind-villain `unmarked` row, never the four tactic Fights).

## User-Visible Impact

On `dashboard.legendary-arena.com/debug/effects`, a new **Mastermind** scope
filter chip appears alongside Hero / Villain, the `byScope` summary shows a
mastermind count, and every mastermind's four tactics render as rows — the
implemented ones (`co2e` Doc Ock "Octet of Valence Electrons" from WP-497, core
Magneto "Crushing Shockwave" from WP-506) `executable` with their handler + WP
+ Decision, the rest `unmarked`. The arc's remaining work becomes a filterable
worklist instead of an invisible gap.

## Context (Read First)

**Why a third feed, not a tactic mechanic ledger.** The hero + villain
ledgers are large derived artifacts with their own generators; tactics do not
fit either scope's schema. The index generator's own design note says reading
committed JSON is sufficient and deliberately keeps the engine out of the
build. So this WP mirrors that: the generator gains a **tactic feed** that
(1) enumerates every mastermind tactic from the card data for identity
(`extId` / `name` / `set` / `mechanic`), and (2) overlays a small committed
**`scripts/coverage/tactic-provenance.json`** for `status` / `handler` / `wp`
/ `decision` — exactly the `mechanic-provenance.json` (WP-493) pattern. A
tactic absent from the provenance map defaults to `unmarked` with blank
handler/wp/decision (the honest "no handler ran" signal). Adding a future
resolver = one provenance row, no generator change.

**`mechanic` for a tactic.** Each tactic is one row; its `mechanic` is the
tactic **slug** (`crushing-shockwave`, `octet-of-valence-electrons`, …), so a
mastermind contributes four distinct rows, one per tactic, matching how the
`card × mechanic` grid reads elsewhere.

**Determinism / boundaries.** This is entirely a build-time coverage artifact
+ its schema + the dashboard reader — **no engine, no `G`, no runtime**. No
`finalStateHash` / `PRE_WP080` surface. The registry edit is a schema-only
additive enum widening (a contract change → a DECISIONS entry, D-24313). The
generator must stay engine-free (reads card data + committed JSON only).

## Design Rationale

**Additive enum widening, not a new artifact.** Folding tactics into the
existing index (new `scope` value) keeps one coverage surface and one CI gate,
rather than a parallel tactic index the dashboard would have to merge. The
dashboard's scope filter is already `EffectIndexEntryScope | 'all'` with
generic equality, so the new value flows through with only a `scopeLabel`
case, a `byScope` count line, a filter chip, and a CSS badge class.

**Card-data enumeration + provenance overlay.** Enumerating tactic identity
from card data means all ~4 tactics per mastermind appear automatically (no
440-row hand-authored file); the tiny provenance overlay carries only the
handful of implemented tactics. This is the WP-493 division of labor
(generated identity, curated provenance).

## Scope (In)

- **Registry (`packages/registry/src/schema.ts`):** add `"mastermind"` to
  `EFFECT_INDEX_ENTRY_SCOPES`; add `mastermind: z.number().int().nonnegative()`
  to `EffectImplementationSummarySchema.byScope` (the `.strict()` object). The
  `superRefine` tally comparison loop already iterates
  `EFFECT_INDEX_ENTRY_SCOPES`, but its **accumulator is a hardcoded literal**
  `const scopeTally = { hero: 0, villain: 0 }` — this is a **REQUIRED edit**,
  not "verify": without `mastermind: 0` there, a mastermind entry does
  `scopeTally['mastermind'] += 1` → `NaN`, and the refinement fails for every
  regenerated index. (`EffectImplementationEntrySchema.scope` and
  `EffectImplementationCardEntrySchema.scope` reference the shared enum, so
  they need no separate edit.) Rebuild the registry `dist` **before** the
  dashboard typecheck (the dashboard imports the widened enum from
  `registry/dist` — a stale dist is a false green).
- **Tooling:**
  - New committed `scripts/coverage/tactic-provenance.json` — a map keyed by
    tactic ext_id → `{ status, handler, wp, decision }` for the **implemented**
    tactics (WP-497 Octet, WP-506 Crushing Shockwave). Documented shape + a
    header note.
  - `scripts/build-effect-implementation-index.mjs`: add a tactic feed —
    `readMastermindTactics()` enumerates `masterminds[].cards[] { tactic: true }`

    stale generator docblock ("Joins the TWO committed mechanic ledgers") and
    the `buildCards` disjoint-id-space comment to include the tactic feed.
  - Regenerate `data/metadata/effect-implementation-index.json` (`pnpm
    effect-index`); `effect-index:check` stays green.
- **Dashboard (`apps/dashboard`):**
  - `composables/useEffectIndex.ts`: add a `'mastermind'` case to `scopeLabel`,
    **and** add `mastermind: 0` to `EMPTY_INDEX.byScope` (typed
