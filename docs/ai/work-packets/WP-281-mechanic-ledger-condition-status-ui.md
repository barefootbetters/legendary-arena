# WP-281 — Mechanic Coverage Dashboard: Condition-Gate Status Display

**Status:** Drafted 2026-06-23

**Scope:** Dashboard only (`apps/dashboard/`). Updates the mechanic coverage display to handle the new "condition" status type introduced by WP-280's ledger schema change.

**Motivation:** WP-280 adds a new "condition" status to the mechanic ledger to properly classify condition-gate mechanics (spectrum requires ≥3 hero classes). The ledger JSON now includes `"status": "condition"` for 5 spectrum rows across ssw2 cards. The dashboard UI must be updated to:
1. Recognize "condition" as a valid status type
2. Display conditions in the mechanic coverage table (either as a separate section or integrated with existing status filters)
3. Update summary counts to include the "condition" category
4. Stop misclassifying spectrum as "unsupported"

**Technical Design:**

### Status Type Expansion
- Ledger now emits: `executable | deferred | condition | unsupported | unmarked` (5 types, up from 4)
- Dashboard currently handles: `executable | deferred | unsupported | unmarked` (4 types)
- Add "condition" to the closed-union TypeScript type and UI filter set

### UI Changes
1. **By-mechanic table:** Add "Condition" section before "Unsupported" in the worklist (conditions are recognized gates, higher priority than unsupported keywords)
2. **Status filter chips:** Add "Condition" chip to the filter ribbon (current: Unsupported, Unmarked, Deferred, Executable, All)
3. **Summary counts:** Update the top-level KPI strip to include condition count (currently shows only Executable/Unsupported/Unmarked/Deferred where present)
4. **Color/badge:** Assign a distinct visual (e.g., `status-condition` CSS class; spectrum icon or "Gate" label) to distinguish from unsupported

### Spectrum-Specific Behavior
- Spectrum will now appear with `status: "condition"` in ledger JSON (5 ssw2 cards)
- Dashboard filters/searches for "spectrum" will find it in the Condition section, not Unsupported
- "Observed in play" column still applies — conditions may also be tracked for runtime hollows if they execute without expected effects (future: distinguish between "condition recognized" vs "condition gating resolved")

### Files to Modify
- `apps/dashboard/src/composables/useMechanicCoverage.ts` — update ledger schema / type guards
- `apps/dashboard/src/views/CoveragePage.vue` — update filter logic, table sections, summary display
- `apps/dashboard/src/components/MechanicCoverageTable.vue` (if separated) or inline — add condition rows
- `apps/dashboard/src/styles/*.css` — add `.status-condition` styling
- `docs/ai/coverage/hero-mechanic-ledger.json` — source (auto-generated by pnpm ledger:heroes; DO NOT manually edit)

### Test Coverage
- Confirm ledger JSON parses and deserializes with `status: "condition"`
- Verify condition status is recognized in the composable
- Verify condition rows display in the table
- Verify filter chips correctly toggle condition visibility
- Verify summary counts include condition rows

### Determinism & Stability
- No game-engine changes (WP-280 is the sole engine touch)
- Ledger artifact (`hero-mechanic-ledger.json`) is regenerated deterministically by `pnpm ledger:heroes`
- Dashboard is a pure UI consumer — no new schema contracts, no API changes

### Hard Dependencies
- **WP-280** ✅ (ledger must emit "condition" status first)
- Dashboard must be deployed AFTER ledger changes are live (no forward-compatibility risk — old ledger won't have "condition" status, new dashboard will safely skip unknown statuses)

### Soft Dependencies
- Visualization / UX improvements (e.g., grouping conditions separately from unsupported) can be iterated post-merge

**Execution Lane:** Lightweight (UI-only change, no engine/server/registry changes, no schema versioning required per D-24028 — the ledger already versioned; dashboard just reads a new field).

**Reserve Decisions:**
- **D-24057** — Condition-gate status is a recognized gate mechanic, not an unsupported keyword. Display order: Executable > Deferred > Condition > Unsupported > Unmarked. Spectrum is the first condition-gate; future conditions (hero-class-match, requires-team, etc. if ever surfaced as keywords) follow the same pattern.
- **D-24058** — Dashboard "condition" visual: status badge = "Condition" label or gate/lock icon. Tooltip: "Recognized condition-gate mechanic; effects execute only when this condition is met."
